# ТЗ: UI разметки портов

Бэкенд и схема данных готовы, см. [Разметка портов](PORT_BOUNDARY_DIRECTION.md).
Здесь — что нарисовать в UI и куда это пишется.

## 1. Цель

Дать оператору за один проход разметить порты коммутаторов (наша сторона /
внешняя + тип стыка) и увидеть, что дало бы определение направления трафика по
портам вместо текущего по сетям.

Пользовательский сценарий целиком:

1. Опросить свитчи по SNMP (уже есть на странице `#snmp`).
2. Задать настройки установки: значение по умолчанию и политику для неизвестной
   стороны.
3. Завести 2–5 правил по описанию или скорости портов → массовая разметка.
4. Доразметить руками то, что правилами не покрылось, опираясь на подсказки из
   трафика.
5. Посмотреть отчёт «сети vs порты» и решить, доверять ли портовой модели.

## 2. Где размещаем

| Экран | Что добавляем |
|---|---|
| `#snmp`, таблица портов свитча | колонки «Сторона» и «Тип стыка» + фильтр |
| `#snmp`, новая вкладка «Разметка портов» | настройки, правила, покрытие, порты по трафику |
| Диагностика (или вкладка там же) | отчёт «Сети vs порты» |

Отдельную страницу заводить не нужно: разметка живёт рядом с SNMP-каталогом,
из которого берутся имена и описания портов.

## 3. Экран «Разметка портов»

### 3.1. Блок «Настройки»

Три контрола, все пишутся в `POST /api/refs/direction-settings`:

| Контрол | Значения | Подпись-пояснение |
|---|---|---|
| Определение направления | По сетям / По портам | «По портам заработает после обновления коллектора» |
| Неразмеченный порт считать | Не определён / Нашей стороной / Внешним | «Не определён — дыры в разметке будут видны в отчётах» |
| Если известна только одна сторона | Не определять / Определять по известной | «Нужно, когда экспортёр не отдаёт выходной интерфейс» |

Словари значений и текущие значения приходят одним запросом
`GET /api/refs/direction-settings` (поле `options`). После сохранения сервер сам
пересчитывает эффективную разметку — перезапросить сводку покрытия.

### 3.2. Блок «Покрытие»

Три плитки:

- **Размечено портов**: `classified / total` и процент.
- **Трафик через размеченные порты**: процент байт за окно.
- **Порты без разметки с трафиком**: количество, кнопка «Показать».

Источник: `GET /api/refs/interface-roles/summary` (по каталогу) и
`GET /api/diagnostics/direction/interfaces?hours=1` (по трафику).

### 3.3. Блок «Правила»

Таблица правил, отсортированная по приоритету:

| Колонка | Поведение |
|---|---|
| Приоритет | число, меньше = раньше применяется; drag или ручной ввод |
| Условие | текстовый шаблон и/или диапазон скорости, см. ниже |
| Сторона | селект: Не менять / Наша сторона / Внешняя |
| Тип стыка | селект, необязательно |
| Вкл | тумблер |
| Действия | Изменить / Удалить |

Форма правила:

- **Поле** — селект: Описание (`descr`) / Alias (`alias`) / Имя (`name`).
- **Шаблон** — текст, regex, моноширинный шрифт; можно оставить пустым.
- **Учитывать регистр** — чекбокс.
- **Скорость порта от / до** — два поля в Мбит/с, оба необязательные.
- Валидация формы: должно быть задано хотя бы одно условие (шаблон или скорость)
  и хотя бы одно назначаемое значение (сторона или тип стыка).

Обязателен **предпросмотр**: по изменению условий (debounce 300 мс) дергаем
`POST /api/refs/interface-role-rules/preview` и показываем «Найдено N портов» +
первые 20 строк (свитч, имя порта, описание, скорость). Без предпросмотра
правило вслепую — главный источник ошибок.

Ошибку невалидного regex показываем прямо под полем: сервер возвращает 400 с
текстом от ClickHouse (RE2 строже JS, поэтому проверка серверная).

### 3.4. Блок «Порты по трафику»

Таблица из `GET /api/diagnostics/direction/interfaces`:

| Колонка | Комментарий |
|---|---|
| Свитч | IP |
| Порт | имя, ниже мелким — описание и скорость |
| Сторона | бейдж; серый если не размечено |
| Источник | `manual` / `rule` / `default`, мелким текстом |
| Тип стыка | бейдж, если задан |
| Трафик | байты за окно, отсортировано по убыванию; в подсказке разбивка на вход и выход |
| ASN за портом | число уникальных автономных систем |
| Подсказка | «похоже на внешний / нашу сторону» на основе числа ASN |
| В каталоге | предупреждение, если порт есть в трафике, но нет в SNMP-каталоге |

Фильтр-переключатель «только без разметки» (`only_unmarked=1`), селект окна
(1 / 3 / 6 / 12 / 24 часа, по умолчанию 1) и порог подсказки (`asn_threshold`,
по умолчанию 50) в дополнительных настройках таблицы.

Рядом с колонкой подсказки — пояснение: за клиентским или участниковым портом
видны единицы автономных систем, за аплинком и магистралью — сотни. Подсказка
не размечает порт сама, оператор подтверждает её кнопкой «Применить».

Смысл экрана: сверху всегда лежат порты, разметка которых даёт наибольший эффект.

## 4. Колонки в таблице портов свитча

На существующей вкладке портов (`#snmp` → выбранный свитч) добавляем две колонки:

- **Сторона** — селект: Не задана / Наша сторона / Внешняя.
- **Тип стыка** — селект типов стыка.
- если значение пришло от правила — показываем серым с подсказкой
  «правило `<rule_id>`»; при ручном выборе значение становится обычным;
- у ручного значения — крестик «сбросить к правилу».

Данные: `GET /api/refs/interface-roles/:ip` — возвращает итоговые `boundary` и
`connectivity`, их источники (`boundarySource`, `connectivitySource`) и отдельно
`manualBoundary` / `manualConnectivity`, так что видно, что именно переопределено.

## 5. Отчёт «Сети vs порты»

Из `GET /api/diagnostics/direction/compare?hours=1`.

Шапка: три числа — **совпадение** (% байт, где обе модели дали одинаковое
направление), **не определено портами** (% байт с `unknown`), объём за окно.
Рядом — переключатель политики односторонней классификации (`one_sided`), чтобы
сравнить оба варианта, не меняя настройки установки.

Ниже — матрица: строки `port_direction`, столбцы `ch_direction`, в ячейках байты
и доля. Диагональ подсвечиваем зелёным, расхождения — жёлтым, `unknown` — серым.

Под матрицей пояснение обычным языком, например:
«7% трафика портовая модель считает транзитом, а текущая — входящим. Обычно это
клиентские сети, которых нет в справочнике `#cidr`.»

Предупреждение над отчётом, если `GET /api/diagnostics/direction/coverage`
показывает меньше ~80% flow с заполненными `in_if` / `out_if`: портовая модель на
таких данных работать не будет, экспортёры не отдают интерфейсы. Если при этом
входной интерфейс приходит почти всегда, а выходной часто в другом формате —
подсказываем включить одностороннюю классификацию.

## 6. Куда что пишется

UI **никогда не пишет в ClickHouse напрямую** — только через API.

| Действие в UI | Запрос | Таблица |
|---|---|---|
| Сохранить настройки | `POST /api/refs/direction-settings` | `net_direction_settings` |
| Сохранить правило | `POST /api/refs/interface-role-rules` | `net_interface_role_rules` |
| Удалить правило | `POST /api/refs/interface-role-rules/delete` | `net_interface_role_rules` (`deleted = 1`) |
| Разметить порт | `POST /api/refs/interface-roles` | `net_interface_roles` |
| Сбросить разметку порта | `POST /api/refs/interface-roles/delete` | `net_interface_roles` (`deleted = 1`) |
| — (автоматически после любой записи) | — | `net_interface_roles_effective` пересчитывается сервером |
| Кнопка «Пересчитать разметку» | `POST /api/refs/interface-roles/rebuild` | `net_interface_roles_effective` |

Тела запросов:

```jsonc
// настройки
{ "directionMode": "prefixes", "defaultBoundary": "unknown", "oneSided": "strict" }

// правило
{ "ruleId": "", "priority": 100, "matchField": "descr",
  "pattern": "^(?:UPLINK|MAG)", "caseSensitive": false,
  "minSpeedMbps": 0, "maxSpeedMbps": 0,
  "boundary": "external", "connectivity": "transit", "comment": "", "enabled": true }

// разметка порта; можно передать массив interfaces для группы портов
{ "switchIp": "172.18.19.55", "ifIndex": 10, "boundary": "internal",
  "connectivity": "customer", "comment": "" }
```

Ответ на запись: `{ ok: true, meta: { …, materialized: { rules, elapsedMs } } }` —
поле `materialized` можно использовать, чтобы после сохранения перезапросить
сводку покрытия.

## 7. Тексты и термины

В интерфейсе — только человеческие подписи, технические значения (`external`,
`customer`) не показываем нигде, кроме подсказок и tooltip'ов.

| Значение | Подпись |
|---|---|
| `internal` | Наша сторона |
| `external` | Внешняя |
| `unknown` | Не задана |
| `customer` | Клиент |
| `transit` | Транзит |
| `pni` / `ppni` | PNI / PPNI |
| `ix` | IX |
| `core` | Ядро |
| `cgnat` | CGNAT |
| `mgmt` | Управление |

Направления в отчёте: `in` → Входящий, `out` → Исходящий, `internal` →
Внутренний, `transit` → Транзит, `unknown` → Не определено.

## 8. Что в этот этап не входит

- Фактическое переключение пайплайна на портовую модель — появится, когда её
  поддержит коллектор GrapesNTA; сейчас настройка только сохраняется.
- Привязка портов к клиентам (лицевым счетам из ERP) — отдельная задача.
- Массовое редактирование выделением строк — при необходимости после первого
  использования.
