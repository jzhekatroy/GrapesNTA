# ТЗ: UI «Порты оборудования»

Бэкенд и схема данных готовы, см. [Разметка портов](PORT_BOUNDARY_DIRECTION.md).
Здесь — что нарисовать в UI и куда это пишется.

## 0. Термины

Слово «порт» в продукте перегружено, поэтому в интерфейсе разводим два понятия и
никогда не смешиваем их в одной подписи:

| Понятие | Как называем в UI | Где живёт |
|---|---|---|
| Физический интерфейс коммутатора (ifIndex, `Ethernet1/13`) | **порт оборудования**, в таблицах просто «Порт» | этот экран, SNMP |
| Номер порта TCP/UDP (`53`, `443`) | **порт приложения** или сразу «сервис» | «Сервисы и порты приложений» |

Раздел меню называется **«Порты оборудования»** — так он не путается с
экраном сервисов, где речь про TCP/UDP.

## 1. Цель

Дать оператору за один проход разметить порты оборудования (наша сторона /
внешняя плюс тип стыка) и увидеть, что дало бы определение направления трафика
по портам вместо текущего по сетям.

Пользовательский сценарий целиком:

1. Опросить коммутаторы по SNMP (уже есть на странице `#snmp`).
2. Задать настройки установки: значение по умолчанию и политику для неизвестной
   стороны.
3. Завести 2–5 правил по описанию или скорости портов → массовая разметка.
4. Доразметить руками то, что правилами не покрылось, опираясь на подсказки из
   трафика.
5. Посмотреть отчёт «сети vs порты» и решить, доверять ли портовой модели.

## 2. Где размещаем

Отдельный пункт меню **«Порты оборудования»** (`#interface-roles`) в разделе
**«Модель сети»** — рядом с «Собственные сети (CIDR)» и «Владельцы L3». Логика
одна: все эти экраны отвечают на вопрос «свой или чужой», просто разными
способами — по адресам, по владельцам, по портам оборудования.

| Экран | Что добавляем |
|---|---|
| Новый `#interface-roles` | настройки, правила, покрытие, порты по трафику, отчёт «сети vs порты» |
| `#snmp`, таблица портов коммутатора | колонки «Сторона» и «Тип стыка» **только на чтение** плюс ссылка «Разметить» |

Почему не вкладкой внутри SNMP: страница SNMP отвечает за опрос (учётные данные,
список коммутаторов, кнопка probe) и относится к разделу «Сбор данных». Разметка
— это классификация трафика, у неё другой владелец и другая частота
использования. Каталог портов при этом общий: имена, описания и скорости
приходят из того же SNMP-опроса.

Регистрируем страницу в `public/data/app-pages.json` (нужно для RBAC) и в `NAV`
в `public/components/shell.jsx`.

## 3. Экран «Порты оборудования»

### 3.1. Блок «Настройки»

Три контрола, все пишутся в `POST /api/refs/direction-settings`. Текущие
значения и словари приходят одним запросом `GET /api/refs/direction-settings`
(поле `options`).

| Контрол | Значения | Подпись-пояснение |
|---|---|---|
| Определение направления | По сетям / По портам оборудования | «По портам заработает после обновления коллектора» |
| Неразмеченный порт считать | Не определён / Нашей стороной / Внешним | «Не определён — дыры в разметке будут видны в отчётах» |
| Если известна только одна сторона | Не определять / Определять по известной | «Нужно, когда экспортёр не отдаёт выходной интерфейс» |

После сохранения сервер сам пересчитывает эффективную разметку — сводку покрытия
нужно перезапросить.

### 3.2. Блок «Покрытие»

Три плитки:

- **Размечено портов**: `classified / total` и процент.
- **Трафик через размеченные порты**: процент байт за окно.
- **Порты без разметки с трафиком**: количество, кнопка «Показать».

Источники: `GET /api/refs/interface-roles/summary` по каталогу и
`GET /api/diagnostics/direction/interfaces?hours=1` по трафику.

### 3.3. Блок «Правила»

Таблица, отсортированная по приоритету: приоритет (меньше — раньше), условие,
сторона, тип стыка, тумблер «включено», действия.

Форма правила:

- поле для текста — селект «Описание / Alias / Имя порта»;
- шаблон — regex, моноширинный шрифт, можно оставить пустым;
- чекбокс «учитывать регистр»;
- скорость порта от / до — два поля в Мбит/с, оба необязательные;
- сторона — селект «Не менять / Наша сторона / Внешняя»;
- тип стыка — селект, необязательно.

Валидация формы: должно быть задано хотя бы одно условие (шаблон или скорость) и
хотя бы одно назначаемое значение (сторона или тип стыка).

Обязателен предпросмотр: по изменению условий с debounce 300 мс дёргаем
`POST /api/refs/interface-role-rules/preview`, показываем «Найдено N портов» и
первые 20 строк (коммутатор, имя порта, описание, скорость). Правило вслепую —
главный источник ошибок.

Невалидный regex показываем прямо под полем: сервер возвращает 400 с текстом от
ClickHouse, потому что RE2 строже JS и проверка серверная.

### 3.4. Блок «Порты по трафику»

Таблица из `GET /api/diagnostics/direction/interfaces`:

| Колонка | Комментарий |
|---|---|
| Коммутатор | IP |
| Порт | имя, ниже мелким — описание и скорость |
| Сторона | бейдж, серый если не размечено |
| Источник | `manual` / `rule` / `default`, мелким текстом |
| Тип стыка | бейдж, если задан |
| Трафик | байты за окно, сортировка по убыванию; в подсказке разбивка на вход и выход |
| ASN за портом | число уникальных автономных систем |
| Подсказка | «похоже на внешний / нашу сторону» плюс кнопка «Применить» |
| В каталоге | предупреждение, если порт есть в трафике, но его нет в SNMP-каталоге |

Фильтры: переключатель «только без разметки» (`only_unmarked=1`), окно
1 / 3 / 6 / 12 / 24 часа (по умолчанию 1), порог подсказки `asn_threshold`
(по умолчанию 50) в дополнительных настройках таблицы.

Рядом с подсказкой поясняющий текст: за клиентским или участниковым портом видны
единицы автономных систем, за аплинком и магистралью — сотни. Сама подсказка
порт не размечает, оператор подтверждает её кнопкой.

Смысл экрана: сверху всегда лежат порты, разметка которых даёт наибольший эффект.

### 3.5. Блок «Сети vs порты»

Отчёт из `GET /api/diagnostics/direction/compare?hours=1`. Держим его на этой же
странице последним блоком (или отдельной вкладкой внутри неё): это проверка
результата разметки, оператор смотрит его сразу после правок, а не идёт в
диагностику.

Шапка: совпадение (процент байт, где обе модели дали одинаковое направление), не
определено портами (процент байт с `unknown`), объём за окно. Рядом
переключатель политики односторонней классификации (`one_sided`), чтобы сравнить
оба варианта, не меняя настройки установки.

Матрица: строки — направление по портам, столбцы — текущее направление, в
ячейках байты и доля. Диагональ зелёная, расхождения жёлтые, `unknown` серый.

Под матрицей пояснение обычным языком, например: «7% трафика портовая модель
считает транзитом, а текущая — входящим. Обычно это клиентские сети, которых нет
в справочнике «Собственные сети (CIDR)».

Над отчётом предупреждение, если `GET /api/diagnostics/direction/coverage`
показывает меньше примерно 80% flow с заполненными `in_if` / `out_if`: на таких
данных портовая модель работать не будет. Если при этом входной интерфейс
приходит почти всегда, а выходной часто в другом формате — подсказываем включить
одностороннюю классификацию.

## 4. Что меняется на странице SNMP

В таблице портов коммутатора (`#snmp` → выбранный коммутатор) добавляем две
колонки только на чтение: «Сторона» и «Тип стыка», с фильтром «показать
неразмеченные». Редактирования здесь нет — вместо этого ссылка «Разметить» ведёт
на `#interface-roles` с преднастроенным фильтром по этому коммутатору.

Данные: `GET /api/refs/interface-roles/:ip` — возвращает итоговые `boundary` и
`connectivity`, их источники (`boundarySource`, `connectivitySource`) и отдельно
`manualBoundary` / `manualConnectivity`, так что видно, что именно переопределено.

Тот же запрос используется на экране разметки, где значения уже редактируемые:
значение от правила показываем серым с подсказкой «правило `<rule_id>`», у
ручного значения — крестик «сбросить к правилу».

## 5. Куда что пишется

UI **никогда не пишет в ClickHouse напрямую** — только через API.

| Действие в UI | Запрос | Таблица |
|---|---|---|
| Сохранить настройки | `POST /api/refs/direction-settings` | `net_direction_settings` |
| Сохранить правило | `POST /api/refs/interface-role-rules` | `net_interface_role_rules` |
| Удалить правило | `POST /api/refs/interface-role-rules/delete` | то же, `deleted = 1` |
| Разметить порт | `POST /api/refs/interface-roles` | `net_interface_roles` |
| Сбросить разметку | `POST /api/refs/interface-roles/delete` | то же, `deleted = 1` |
| Пересчитать разметку | `POST /api/refs/interface-roles/rebuild` | `net_interface_roles_effective` |

После любой записи сервер пересчитывает `net_interface_roles_effective` сам.

Тела запросов:

```jsonc
// настройки
{ "directionMode": "prefixes", "defaultBoundary": "unknown", "oneSided": "strict" }

// правило
{ "ruleId": "", "priority": 100, "matchField": "descr",
  "pattern": "^(?:UPLINK|MAG)", "caseSensitive": false,
  "minSpeedMbps": 0, "maxSpeedMbps": 0,
  "boundary": "external", "connectivity": "transit", "comment": "", "enabled": true }

// разметка порта; можно передать массив interfaces для группы портов
{ "switchIp": "172.18.19.55", "ifIndex": 10, "boundary": "internal",
  "connectivity": "customer", "comment": "" }
```

Ответ на запись: `{ ok: true, meta: { …, materialized: { rules, elapsedMs } } }` —
по `materialized` удобно понять, что пора перезапросить сводку покрытия.

## 6. Подписи

Технические значения (`external`, `customer`) не показываем нигде, кроме
подсказок и tooltip'ов.

| Значение | Подпись |
|---|---|
| `internal` / `external` / `unknown` | Наша сторона / Внешняя / Не задана |
| `customer` / `transit` | Клиент / Транзит |
| `pni` / `ppni` / `ix` | PNI / PPNI / IX |
| `core` / `cgnat` / `mgmt` | Ядро / CGNAT / Управление |

Направления: `in` — Входящий, `out` — Исходящий, `internal` — Внутренний,
`transit` — Транзит, `unknown` — Не определено.

## 7. Вне этого этапа

Фактическое переключение пайплайна на портовую модель (появится, когда её
поддержит коллектор GrapesNTA; сейчас настройка только сохраняется), привязка
портов оборудования к клиентам из ERP, массовое редактирование выделением строк.
