# ТЗ: доведение «Наблюдений» до рабочего состояния

Статус: черновик к согласованию. Дата: 2026-07-27.

Функция «Наблюдения» — личные доски пользователя: набор фильтров + виджеты, которые
обновляются сами (live) и по расписанию превращаются в отчёт. Сейчас функция работает
частично: часть обещанных возможностей есть только в модели данных и в документации.

Задача ТЗ — закрыть разрыв между тем, что обещано, и тем, что работает, и сделать
функцию предсказуемой в эксплуатации.

## 0. Границы работ

**Входит:** расписание и доставка отчётов, честное поведение интерфейса, устойчивость
воркера, удобство работы с доской.

**Не входит** (отдельные задачи, наблюдения от них не зависят):

- пороговые алерты и детект аномалий (ML) — это отдельная подсистема;
- массовые доски «на каждого клиента» — им нужен другой путь к данным
  (общий агрегат `traffic_entity_1m`), а не масштабирование материализации наблюдений;
- перевод рулапов на минутную детализацию — заметная переделка, делаем только если
  5 минут реально мешают (см. п. 8, открытые вопросы).

**Затрагиваемый код** (в GrapesNTA — вендорная копия `deploy/ui/app/server/`):

| Файл | Что там |
|---|---|
| `server/observations.js` | модель, нормализация, preview, отчёты, квоты |
| `server/observations-store.js` | чтение/запись в ClickHouse |
| `server/observations-rollup.js` | catch-up рулапов, статусы, восстановление |

# Блок 1. Честное поведение (P0)

Здесь всё про то, что интерфейс или документация обещают, а код не делает. Это самая
дорогая категория дефектов: пользователь строит план работы на неверных ожиданиях.

## 1.1 Расписание отчётов работает по-настоящему

**Сейчас.** В модели есть `report.cron` (по умолчанию `0 8 * * *`) и
`report.timezone` (`Europe/Moscow`). Ни то, ни другое не участвует в запуске.
Фактическое правило — `isReportDue()` в `server/observations.js:959`: отчёт считается
просроченным, если за последние 20 часов не было успешного запуска. Проверка идёт из
цикла воркера не чаще раза в час. То есть время формирования отчёта плывёт и зависит от
момента предыдущего успешного запуска.

**Делаем.** Заменяем свободный cron на структурированное расписание — его понятно
показать в интерфейсе и не нужно тянуть парсер cron.

```
report.schedule = {
  kind: 'daily' | 'weekly' | 'monthly',
  time: 'HH:MM',            // локальное время в timezone наблюдения
  weekday: 1..7,            // только для weekly, 1 = понедельник
  day: 1..28,               // только для monthly
  timezone: 'Europe/Moscow' // IANA-зона, по умолчанию из настроек инстанса
}
```

Логика «пора запускать»: вычисляем ближайший плановый момент, предшествующий текущему
времени, в зоне `timezone`. Если для этого момента нет запуска со статусом `ok` —
запускаем. Допуск на опоздание — 6 часов (если воркер лежал дольше, пропущенный слот
не догоняем, чтобы не сыпать отчётами задним числом).

Проверка due переносится на тик воркера (раз в минуту) вместо часа, иначе точность
расписания теряется. Стоимость проверки — один запрос к `observation_runs` на
наблюдение, это дёшево.

**Миграция.** Существующие записи: `cron = '0 8 * * *'` → `{kind: 'daily', time: '08:00'}`.
Разбор произвольного cron не делаем: если строка не совпала с шаблоном
`M H * * *`, ставим 08:00 и пишем предупреждение в лог. Поле `report.cron` удаляем из
модели после миграции.

**Приёмка.** Отчёт с расписанием «ежедневно 08:00, Europe/Moscow» формируется между
08:00 и 08:02 по Москве. Повторный тик в тот же день отчёт не дублирует. При остановке
воркера на сутки после старта формируется ровно один отчёт, а не серия.

## 1.2 Период отчёта считается в таймзоне пользователя

**Сейчас.** `reportWindow()` в `server/observations.js:382` считает «вчера» как
календарные сутки UTC. Для Москвы это интервал с 03:00 предыдущего дня до 03:00
текущего — то есть не вчерашние сутки. `report.timezone` игнорируется.

**Делаем.** Границы периода считаются в `report.schedule.timezone`. Для `yesterday` —
от 00:00 до 24:00 местного времени предыдущих календарных суток. Для `last_24h`
поведение не меняется (скользящее окно).

В заголовке отчёта явно печатаем период с указанием зоны, например
«25 июля 2026, 00:00–24:00 (Europe/Moscow)». Сейчас зона не указана, и по числам
невозможно понять, какая имелась в виду.

**Важно про ClickHouse.** Переменная `CLICKHOUSE_TIMEZONE` по умолчанию `UTC`
(`server/clickhouse.js:104`), а воркер режет бакеты арифметикой по UTC-эпохе
(`observations-rollup.js:81`). При `CLICKHOUSE_TIMEZONE ≠ UTC` возможен сдвиг на один
бакет. Границы окна передаём в запрос как явные UTC-метки, чтобы результат не зависел
от настройки сервера.

**Приёмка.** Отчёт «за вчера» для московской зоны совпадает по сумме байт с ручным
запросом за местные сутки с точностью до округления бакетов. Смена
`CLICKHOUSE_TIMEZONE` на `Europe/Moscow` не меняет цифры в отчёте.

## 1.3 Отправка отчётов на почту

**Сейчас.** Поле `report.emailTo` заполняется и сохраняется, но не читается нигде.
В HTML-отчёте стоит заглушка «Email-отправка будет добавлена позже»
(`server/observations.js:897`). В репозитории нет ни SMTP-клиента, ни какой-либо другой
серверной подсистемы уведомлений, которую можно переиспользовать.

**Делаем.**

*Зависимость.* `nodemailer` в `package.json` UI-образа и образа `grapes-analytics`
(отправляет воркер, не UI).

*Настройки SMTP.* Новая таблица по образцу `net_snmp_settings` — одна строка,
`ReplacingMergeTree`, плюс вью `*_current`:

```
default.app_smtp_settings
  settings_id  String DEFAULT 'global'
  host         String
  port         UInt16 DEFAULT 587
  secure       UInt8  DEFAULT 0        -- 1 = implicit TLS (465)
  username     String
  password     String                  -- в открытом виде, как community в SNMP
  from_email   String
  from_name    String DEFAULT 'GrapesNTA'
  enabled      UInt8  DEFAULT 0
  updated_at   DateTime('UTC') DEFAULT now()
```

Пароль лежит открытым текстом — так же, как SNMP community. Отдельного хранилища
секретов в продукте нет, вводить его в рамках этой задачи не будем. В API пароль
никогда не отдаём: только флаг «задан / не задан».

Экран настроек — в разделе «Настройки», рядом с SNMP. Обязательна кнопка «Проверить
отправку»: посылает тестовое письмо на адрес текущего пользователя и показывает ошибку
SMTP целиком, без сокращений.

*Отправка.* После успешного формирования отчёта воркер, если `emailTo` не пуст и SMTP
включён, отправляет письмо: тема «GrapesNTA: <имя наблюдения> — <период>», тело — тот
же HTML, что и артефакт, CSV — вложениями. Одна попытка плюс два повтора с задержкой
1 и 5 минут. Ошибка отправки **не** делает запуск неуспешным: отчёт сформирован, это
фиксируется отдельно.

*Учёт доставки.* Добавляем в `observation_runs` колонки через
`ALTER TABLE ... ADD COLUMN IF NOT EXISTS` (новый файл слоя, идемпотентно при повторном
`apply.sh`):

```
email_status String DEFAULT ''    -- '' | 'skipped' | 'sent' | 'error'
email_to     String DEFAULT ''    -- фактические получатели, через запятую
email_error  String DEFAULT ''
```

*Валидация.* `emailTo` — до 10 адресов, проверка формата на входе API.

**Приёмка.** При настроенном SMTP отчёт приходит на указанные адреса с вложенными CSV.
При неверном пароле SMTP запуск помечается `ok`, доставка — `error` с текстом ошибки,
и это видно в истории запусков. При выключенном SMTP поле `emailTo` в интерфейсе
показывает подсказку «SMTP не настроен» со ссылкой на настройки.

## 1.4 История запусков видна в интерфейсе

**Сейчас.** Запуски пишутся в `observation_runs`, артефакты складываются в
`server/data/observation_runs/<id>/<runId>/`, API `GET /api/observations/:id/runs` и
`.../artifact` работают, клиентские обёртки в `public/data/api.js:651` есть — но
`public/pages/observations.jsx` их не вызывает. Сформированный отчёт получить из
интерфейса невозможно.

**Делаем.** На плитке в развёрнутом виде — вкладка «Отчёты»: таблица последних 20
запусков (когда, период, статус, длительность, статус письма) и ссылки «HTML» и «CSV»
на артефакты. Ручной запуск («Сформировать отчёт») после завершения обновляет этот
список.

Если артефакт удалён с диска (каталог `server/data` не расшарен между UI и воркером —
типичная ошибка развёртывания), ссылка отдаёт понятное «Артефакт недоступен: UI и
analytics не делят каталог данных», а не 404 без объяснений.

**Приёмка.** После ручного запуска в списке появляется строка, HTML открывается в новой
вкладке, CSV скачивается.

## 1.6 Квоты и предупреждения показываются

**Сейчас.** API отдаёт в каждом элементе списка вычисленные `quotas` и `warnings`
(`server/observations.js:249`), но в `public/` они не рендерятся нигде. Лимит

**Приёмка.** При 15 занятых слотах попытка включить шестнадцатое обновление даёт
диалог со списком занявших, а не только текст ошибки.

## 1.7 Документация приводится в соответствие с кодом

`docs/observations.md` описывает поведение, которого нет. Конкретно:

| Утверждение в документе | Как в коде |
|---|---|
| native scope (VLAN/ASN/направление/…) читает готовые агрегаты `traffic_*` | native-путь идёт в `explorerTimeseries` → `flows_raw`; агрегаты `traffic_*` не используются вовсе |
| «прямой авто-poll `flows_raw` для live запрещён» | и воркер, и preview читают `flows_raw` |
| native tier определяется набором полей (`NATIVE_FILTER_FIELDS`) | константа объявлена и экспортируется, но в `classifyScope` не используется: native только при полном отсутствии фильтров и группировки |
| concurrency воркера 2 | в коде и в compose — 1 |
| backfill 24h через `OBSERVATION_ROLLUP_BACKFILL_HOURS` | переменная называется `OBSERVATION_ROLLUP_MAX_BEHIND_HOURS`, и это не backfill, а предел отставания |
| catch-up «до 15 минут за проход» | в коде по умолчанию 60, в compose переопределено на 15 |
| в интерфейсе есть история отчётов | не реализована (п. 1.4) |
| конструктор на `#observations` | конструктор только в Explorer |

Отдельно: либо задействовать `NATIVE_FILTER_FIELDS` в классификации (тогда часть
наблюдений перестанет требовать материализации и слоты освободятся), либо удалить
константу. Решение — в открытых вопросах (п. 8), потому что это меняет поведение, а не
только текст.

# Блок 2. Устойчивость (P1)

## 2.1 Отмена задания и сброс зависшего

**Сейчас.** Блокировка мягкая: воркер просто пишет наблюдению `status: 'running'`
(`observations-rollup.js:220`). Отменить работающий catch-up нельзя. Зависшее `running`
сбрасывается только при старте воркера — `recoverStuckRunning()`
(`observations-rollup.js:282`) переводит все `running` в `queued`. То есть лечение —
перезапуск контейнера.

**Делаем.**

- `POST /api/observations/:id/cancel` — ставит флаг `materialize.cancelRequested`.
  Воркер проверяет флаг между шагами catch-up (шаг — один интервал в пределах
  `OBSERVATION_ROLLUP_SHOT_MINUTES`) и корректно останавливается, оставляя курсор на
  последнем завершённом бакете, со статусом `idle`.
- Watchdog по времени: если `running` держится дольше
  `OBSERVATION_ROLLUP_STUCK_SEC` (по умолчанию 900), запись переводится в `error` с
  текстом «превышено время выполнения» независимо от перезапуска воркера. Пишем в
  статус время начала шага, чтобы это можно было определить.

**Приёмка.** Тяжёлое наблюдение отменяется из интерфейса за время до одного шага.
Убитый `-9` воркер не оставляет наблюдение в `running` дольше 15 минут.

## 2.2 Повторы с задержкой и видимая ошибка

**Сейчас.** При исключении статус становится `error`, текст падает в
`materialize.lastError` (`observations-rollup.js:272`). Следующий тик через минуту
подхватывает запись снова, потому что `error` идёт вторым в приоритете. Если ошибка
устойчивая (например, синтаксис в фильтре), это бесконечный цикл раз в минуту с полной
нагрузкой на ClickHouse. Экспоненциальной задержки нет.

**Делаем.** Счётчик `materialize.failCount` и `materialize.nextAttemptAt`. Задержка:
1, 5, 15, 60 минут, дальше 60. После успешного шага счётчик сбрасывается. После 10
неудач подряд обновление выключается автоматически со статусом `error` и пометкой
«остановлено после 10 ошибок» — чтобы не жечь ресурсы на заведомо нерабочей
конфигурации.

Текст ошибки на плитке показываем сразу, а не только в диагностике: короткая плашка
«Ошибка подготовки данных» с раскрытием полного текста.

**Приёмка.** Наблюдение с заведомо неверным фильтром делает 10 попыток с растущими
интервалами и отключается; в интерфейсе видна причина.

## 2.3 Бэкфилл истории при создании

**Сейчас.** Курсор при первом включении ставится на `createdAt`
(`server/observations.js:188`), и `resolveCatchupFrom` никогда не уходит раньше
(`observations-rollup.js:123`). График нового наблюдения начинается с нуля, хотя данные
за прошлые дни лежат в `flows_raw`. Для наблюдения с окном «7 дней» это означает
неделю бесполезной доски.

**Делаем.** При включении обновления считаем историю назад на
`OBSERVATION_BACKFILL_HOURS` (по умолчанию 24 часа, максимум ограничен доступной
глубиной `flows_raw` и TTL рулапов 14 дней). Бэкфилл — отдельное задание с приоритетом
**ниже** обычного catch-up: сначала догоняем настоящее время, историю добираем в
свободные тики. Иначе новое наблюдение с большим окном заблокирует всю очередь при
concurrency = 1.

Прогресс показываем на плитке: «история: 6 из 24 ч».

**Приёмка.** Созданное наблюдение в течение часа набирает сутки истории, при этом
живые данные остальных наблюдений не отстают.

## 2.4 Честный индикатор актуальности

**Сейчас.** `rollupStatusLabel()` (`public/pages/observations.jsx:140`) показывает
«готовим данные…», «отставание 900с», «нужна подготовка». Пользователь не понимает,
на какой момент данные на графике актуальны. При этом нормальное отставание тут всегда
не меньше 5–10 минут: бакет 5 минут (`ROLLUP_BUCKET_SEC = 300`), плюс воркер
сознательно отступает на один закрытый бакет для опоздавших потоков
(`observations-rollup.js:189`).

**Делаем.** На плитке всегда — «данные по 13:25» (время последнего готового бакета в
зоне пользователя). Проблемные состояния добавляются к этой строке, а не заменяют её.
В подсказке — объяснение, почему нормальная задержка около 10 минут.

**Приёмка.** Пользователь по плитке отвечает на вопрос «на какой момент эти цифры» без
захода в диагностику.

## 2.5 Лимит материализаций

Жёсткий лимит по умолчанию **снят**. При необходимости потолок включается
переменной `OBSERVATION_MAX_MATERIALIZE` (положительное число). В интерфейсе
показывается число активных подготовленных наблюдений.

## 2.6 Таблица `observation_rollups_1m`

Таблица разворачивается схемой (`deploy/schema/70_observations/02_observation_rollups_1m.sql`),
но в коде на неё **ноль ссылок**. Она вводит в заблуждение при разборе инцидентов —
кажется, что где-то есть минутные данные.

Решение: убрать файл из слоя схемы, таблицу на существующих стендах удалить вручную
(предварительно проверив, что она пустая). Если позже понадобится минутная детализация
(п. 8), таблица создаётся заново вместе с кодом, который её пишет.

## 2.7 Диагностика причин отставания

**Сейчас.** Панель «Диагностика воркера» (`public/pages/observations.jsx:684`) показывает
heartbeat и статистику. Ответа на вопрос «почему это наблюдение отстаёт» она не даёт.

**Делаем.** Для отстающего наблюдения показываем: длительность последних шагов
catch-up, сколько строк `flows_raw` просмотрено, глубину очереди и позицию в ней,
текущий `concurrency`. Это позволяет отличить «воркер не успевает физически» от
«наблюдение стоит в очереди за тяжёлым соседом» — сейчас это неразличимо.

# Блок 3. Удобство (P2)

## 3.1 Дублирование наблюдения

Кнопка «Дублировать»: копия определения с именем «<имя> (копия)», обновление
выключено (чтобы не съесть слот квоты неожиданно). Сейчас единственный способ сделать
похожее наблюдение — заново собрать фильтры в Explorer.

## 3.2 Папки, теги, описание

Поля `folder` и `description` уже в модели. Выводим: описание — в настройках плитки и
как подсказка на доске; папка — группировка доски с возможностью свернуть группу.
Значение по умолчанию `Мои наблюдения` сохраняем. Теги отдельным полем **не** вводим —
папки и так закрывают потребность, а два механизма группировки запутают.

## 3.3 Шаринг доски

Поле `isShared` есть, ACL в бэкенде реализован (`server/observations.js:262`), в
интерфейсе переключателя нет. Добавляем переключатель «Доступно всем» в настройках
плитки (только владельцу) и пометку «общее» на чужих наблюдениях в списке. Права на
редактирование остаются только у владельца — как сейчас.

## 3.4 Сравнение с прошлым периодом

На графике — необязательная вторая линия «то же время неделю назад» (для суточных окон)
или «предыдущий период той же длины». Читается из тех же рулапов, дополнительной
подготовки данных не требует. Это самая частая операция при разборе «стало больше или
меньше», сейчас её приходится делать глазами по двум скриншотам.

## 3.5 Выгрузка CSV из живой плитки

Сейчас CSV существует только как артефакт отчёта, то есть нужно сформировать отчёт.
Добавляем кнопку «CSV» в развёрнутой плитке — выгружает то, что на экране (ряды графика
и таблицу топа) за текущее окно.

## 3.6 Раскладка доски

Порядок плиток и размер (одна или две колонки) с сохранением в новом поле `layout`.
Сетка сейчас жёсткая, две колонки (`app.css:4194`). Делаем последним пунктом: это
чистое удобство, и оно не блокирует ничего другого.

# 7. Порядок работ

Внутри каждого этапа пункты независимы, между этапами — последовательно.

**Этап 1 (P0, честность).** Расписание и таймзона (1.1, 1.2) → история запусков в
интерфейсе (1.4) → почта (1.3) → квоты в интерфейсе (1.6) → чистка мёртвых полей (1.5)
→ документация (1.7).

Почта идёт после истории запусков намеренно: без видимой истории невозможно проверить,
что письмо ушло.

**Этап 2 (P1, устойчивость).** Отмена и watchdog (2.1) → повторы с задержкой (2.2) →
бэкфилл (2.3) → индикатор актуальности (2.4) → удаление лишней таблицы (2.6) →
диагностика (2.7).

**Этап 3 (P2, удобство).** Дублирование (3.1) → папки и описание (3.2) → шаринг (3.3)
→ сравнение периодов (3.4) → CSV (3.5) → раскладка (3.6).

Проверка каждого пункта — на реальных данных стенда, а не на синтетике: расписание
проверяется реальным прохождением ночи, бэкфилл — на существующей глубине `flows_raw`.

# 8. Принятые решения и открытые вопросы

**Решено.**

1. **Native scope не трогаем.** `NATIVE_FILTER_FIELDS` остаётся неиспользованной, из
   классификации ничего не меняем. Задействование готовых агрегатов `traffic_*` для
   наблюдений по VLAN/ASN/направлению — отдельная задача: она освободит слоты квоты, но
   меняет поведение уже созданных наблюдений и требует проверки, что все нужные разрезы
   в агрегатах действительно есть. В рамках этого ТЗ только приводим документацию в
   соответствие с фактическим поведением (п. 1.7).
2. **Детализация остаётся 5 минут.** Минутные рулапы не вводим. Задержку около 10 минут
   не убираем, а честно показываем в интерфейсе (п. 2.4).

**Открыто.**

3. **Шифрование пароля SMTP.** В ТЗ заложено хранение открытым текстом, как SNMP
   community. Вопрос — вводить ли шифрование на уровне продукта; это отдельная задача,
   затрагивающая и SNMP.
4. **Кому доступны настройки SMTP.** Только администратору или отдельное право в RBAC.
