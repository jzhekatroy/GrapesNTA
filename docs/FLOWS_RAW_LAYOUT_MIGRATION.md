# Перевод flows_raw на новую раскладку

Инструкция для установки, которая ещё работает на прежней раскладке сырых
потоков. Проверена на 5.188.236.212 22 сентября 2026 года.

## Зачем

Почти каждый запрос разбора трафика — это окно по времени плюс фильтр по
коммутатору и порту. Прежняя таблица была отсортирована только по времени
прихода с наносекундной точностью. Такой ключ почти уникален, поэтому
разреженный индекс отсекал только само окно, а номера портов и адреса
экспортёров лежали размазанными по файлу.

Новая раскладка сортирует по пятиминутному отрезку времени, адресу экспортёра
и номерам портов. Само время стоит последним в ключе: внутри группы оно снова
возрастает, поэтому колонка времени сжимается не хуже прежней. Время переведено
в секундную точность, сжатие — с ZSTD на LZ4.

Замеры на стенде, одинаковые запросы интерфейса, окно пять минут, кэши сброшены:

| запрос | было | стало | выигрыш |
|---|---|---|---|
| сводка за окно | 0.240 с | 0.101 с | 2.4 раза |
| топ ASN | 0.234 с | 0.096 с | 2.4 раза |
| топ IP-источников | 0.485 с | 0.255 с | 1.9 раза |
| график по времени | 0.261 с | 0.076 с | 3.4 раза |
| сводка с фильтром по описанию порта | 0.788 с | 0.077 с | 10 раз |
| топ ASN с фильтром по описанию порта | 0.579 с | 0.074 с | 7.8 раза |
| топ IP с фильтром по описанию порта | 0.580 с | 0.073 с | 7.9 раза |

Диск: 35 байт на строку вместо 58.5, сжатие 5.9 вместо 3.76.

Запросы с фильтром по порту выигрывают больше всех, потому что читают только
нужные гранулы: 320 тысяч строк вместо 10.4 миллионов на том же окне.

## Что происходит с данными

Коллектор как писал в `default.flows_raw`, так и пишет — его не перезапускают
и не пересобирают. Время он передаёт как `time.Time`, а драйвер приводит
значение к типу колонки сам, поэтому смена `DateTime64(9)` на `DateTime`
проходит незаметно.

Прежняя таблица переезжает в `flows_v1` и доживает свой TTL, после чего
удаляется. Никакого переливания данных нет.

На это время читатели смотрят в `flows_all` — таблицу-обёртку `ENGINE = Merge`
поверх новой и старой. Через неё видно обе, поэтому история не рвётся ни на
минуту. Проверить обёртку на конкретной установке можно отдельно:

```
scripts/probe-merge-wrapper.sh
```

Скрипт создаёт игрушечные таблицы в отдельной базе, проверяет `PREWHERE` по
`date`, отсечение партиций, скип-индексы, приведение типов времени и `JOIN`,
и в конце убирает за собой.

## Порядок действий

Обёртка создаётся первой, до перевода читателей: её регулярное выражение пока
совпадает только с текущей таблицей, поэтому читатели переходят на неё, ничего
не замечая, а подмена происходит уже под ними.

1. Убедиться, что на таблице нет незавершённых мутаций. Мутация `MATERIALIZE
   TTL` на сырых потоках занимает диск целиком на часы и не даст сделать
   подмену:

   ```
   SELECT table, mutation_id, command, parts_to_do
   FROM system.mutations WHERE table = 'flows_raw' AND NOT is_done;
   ```

   Если такая мутация есть и срок хранения продлевали, а не сокращали, она
   ничего не удаляет и её можно снять:

   ```
   KILL MUTATION WHERE database = 'default' AND table = 'flows_raw'
     AND mutation_id = '<из запроса выше>';
   ```

2. Выложить код и создать обёртку:

   ```
   cd /opt/GrapesNTA && git pull
   python3 scripts/migrate-flows-layout.py --wrapper
   ```

   Скрипт сверит, что за вчерашний день обёртка отдаёт те же строки, байты и
   пакеты, что и сама таблица.

3. Перевести читателей и пересобрать их:

   ```
   scripts/switch-readers-to-flows-all.sh on
   ./deploy/deploy.sh --no-pull ui worker detection
   ```

   Проверка здоровья интерфейса должна показать
   `"flowsRawTable":"flows_all","flowsRawWriteTable":"flows_raw"`.

   Здесь стоит задержаться и убедиться, что обнаружение атак идёт по минутам,
   а сводки наполняются. Данные при этом ещё прежние, риска нет.

4. Подменить таблицы:

   ```
   python3 scripts/migrate-flows-layout.py --apply
   ```

   Занимает секунды. Сразу после этого в новой таблице должны появиться строки,
   а время в них — совпадать с текущим:

   ```
   SELECT count(), toString(max(time_received_ns)), toString(now())
   FROM default.flows_raw;
   ```

5. Сверить, что ничего не встало: обнаружение атак продвигается по минутам, в
   `traffic_dashboard_1m` нет пропущенных минут вокруг момента подмены, объём
   строк в минуту не изменился.

Если что-то не так, откат возвращает прежнюю таблицу на место одной командой
и не теряет новых строк:

```
python3 scripts/migrate-flows-layout.py --rollback
```

## Через десять дней

Когда `flows_v1` доживёт свой TTL, читателей возвращают на физическую таблицу
и лишнее убирают:

```
scripts/switch-readers-to-flows-all.sh off
./deploy/deploy.sh --no-pull ui worker detection
```

```
DROP TABLE default.flows_all;
DROP TABLE default.flows_v1;
```

## О чём помнить

Обёртка не таблица, и в двух местах это важно.

`ALTER ADD COLUMN` она принимает молча и вниз не передаёт — первое же чтение
такой колонки падает с `NOT_FOUND_COLUMN_IN_BLOCK`. `MODIFY TTL` отклоняет
сразу. Поэтому имя для чтения и имя для изменения схемы разведены:
`CLICKHOUSE_FLOWS_RAW_TABLE` и `CLICKHOUSE_FLOWS_RAW_WRITE_TABLE`.

Запрос `max(time_received_ns)` на обычной таблице берётся из метаданных частей
и отвечает мгновенно, а через обёртку эта оптимизация отключается и запрос
читает колонку целиком: на стенде 56 секунд против 0.7. Проверки отставания
коллектора в сборщике сводок поэтому смотрят в физическую таблицу
(`TRAFFIC_ROLLUP_FLOWS_LIVE_TABLE`), а сами расчёты — в обёртку
(`TRAFFIC_ROLLUP_FLOWS_TABLE`).

Доли секунды в списке последних потоков теперь всегда `.000`: время хранится с
точностью до секунды. Ни на дедупликацию, ни на порядок в обнаружении атак,
ни на границы окон сводок это не влияет — проверено, долями секунды нигде не
пользуются.

## Что осталось сделать отдельно

Колонки `sequence_num`, `ip_ttl` и `ip_tos` никем не читаются и занимают около
103 ГиБ. Убрать их из схемы нельзя без пересборки коллектора: он перечисляет
их в списке вставки. Это отдельная задача.

Группировка по клиентам кабинета остаётся тяжёлой: 27 секунд и 3.8 ГиБ памяти
на пятиминутном окне даже на новой раскладке. Причина не в раскладке, а в том,
что условие «этот клиент с любой стороны» — это ИЛИ по двум колонкам. Тоже
отдельная задача.
