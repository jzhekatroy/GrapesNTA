# API интеграция ERP — раздел администрирования (UI)

Статус: план согласован (обсуждение с Владиславом, 2026-10-22). Реализация не начата.

Задача: раздел «API интеграция ERP» в меню «Администрирование» — управление API-клиентами
(подключениями ERP) через UI вместо/рядом с CLI `server/api-client-create.js`. Фундамент
(таблица `app_api_clients`, OAuth-роуты `/api/v1`, токен-стор) реализован в задаче
[ERP_USERS_API.md](ERP_USERS_API.md).

## 1. Зафиксированные решения

| Вопрос | Решение |
| --- | --- |
| Права | Свой ресурс `api-integration-erp` (постраничная модель RBAC). Дефолт: выключено для всех ролей, кроме Administrator |
| Пересоздание | Как в CLI: новый **client_id + новый секрет**. Старый client_id отключается, его токены отзываются, запись остаётся в таблице со статусом «отключён» (история для журнала) |
| Удаление | Да (доработка после ревью): полное удаление строки из БД с подтверждением, токены отзываются, история действий остаётся в журнале аудита |
| Имена подключений | Уникальны среди активных (доработка после ревью): дубль → 409. Деактивированное имя освобождается |
| Свои креды вручную | Инпуты client_id + секрет, минимум **12 символов**, секрет хранится bcrypt-хэшем, уникальность client_id (409 при коллизии) |
| Отключить/Включить | Отключённое подключение перестаёт выдавать токены (существующие отзываются при отключении); включение возвращает в строй с теми же кредами |
| URL и название | `#api-integration-erp`, пункт «API интеграции» в разделе «Администрирование». Название обобщено под будущие публичные API (правка после ревью: было «API интеграция ERP»), id страницы/URL не менялись |
| Последняя активность | Да — метка «когда ERP последний раз обменял токен/звал API», обновление не чаще раза в минуту |
| Проверка подключения | Кнопка **«Монитор»**: панель с двумя сторонами — готовность NTA + активность ERP за сутки; плюс форма «Проверить пару id+секрет» (см. §3) |
| TTL токена | Показываем на странице (дефолт 3600с, env `API_TOKENS_TTL_SEC`) |
| IP-allowlist | Не делаем (отложено) |

Стиль UI — как страница «Диагностика» (`#diagnostics`, см. `public/pages/erp-piterix.jsx`):
Card-блоки, простые инпуты, таблицы, кнопки `btn btn--primary`, client_id моноширинным.

CLI `server/api-client-create.js` остаётся без изменений — работает поверх той же таблицы.

## 2. Права и доступ

Модель RBAC постраничная: ресурс права = id страницы из `public/data/app-pages.json`
(`server/rbac/permissions.js`, `server/rbac/resources.js`).

- Новый пункт в `app-pages.json` автоматически создаёт ресурс: тумблер появляется в
  «Пользователи и права» → вкладка «Роли» → редактирование роли (матрица «Доступ»/«Запись»
  по всем страницам). Настраивать вручную ничего не нужно.
- Дефолт нового ресурса — выключено для всех ролей (в матрице нет строки → нет доступа),
  роль `Administrator` проходит мимо проверок.
- Сайдбар фильтруется по тем же правам (`filterNav` в `components/shell.jsx`) — пункт сам
  скроется у тех, кому не дали.
- API-роуты закрыты серверно через `server/rbac/api-map.js`:
  `/api/admin/api-clients` → ресурс `api-integration-erp`; GET требует «Доступ»,
  мутации — «Запись».

Где настраивается: «Пользователи и права» (`#users`) → вкладка «Роли» → карандаш у роли.
Персональные оверрайды ALLOW/DENY — в карточке пользователя на вкладке «Пользователи».

## 3. Кнопка «Монитор» и проверка пары

Секрет API-клиента хранится **только bcrypt-хэшем** и показывается один раз при выпуске.
Восстановить текст из хэша нельзя. Опросить ERP тоже нельзя: направление связи обратное
(ERP ходит в NTA, адреса ERP у NTA нет). Поэтому полная картина складывается из двух
независимых инструментов:

1. **«Монитор» (кнопка в строке подключения)** — панель с обеими сторонами:
   - *Сторона NTA*: подключение активно; токен выпускается (тестовый токен тем же
     механизмом, что `/api/v1/oauth/token`, сразу отзывается); TTL токена.
   - *Сторона ERP*: статистика за сутки (обменов токеном, API-запросов — счётчики
     в SQLite-сторе), последний приход, последние операции из журнала аудита
     (события с актёром `api:<имя>`).
   Кнопка не «проверяет подключение» и не опрашивает ERP — она показывает готовность
   нашей стороны и фактическую историю приходов ERP. Если счётчики нулевые и «последний
   приход: никогда» — ERP до нас не доходил (не настроен / секрет не тот / сеть);
   если приходы есть, а пользовательские операции не появляются — ERP подключён,
   но пока ничего не делает.
2. **«Проверить пару id+секрет» (форма с двумя инпутами)** — админ вставляет открытый
   текст секрета, сервер делает тот же `bcrypt.compare`, что `/oauth/token`, и отвечает
   «совпадает / не совпадает». Закрывает опасный сценарий ручного ввода: опечатка при
   переносе секрета в ERP → ERP получает 401, хотя «подключение активно».

Полный обмен с получением настоящего токена остаётся через curl (NTA_API_TEST.md) —
для приёмки и отладки, из UI он не нужен.

## 4. Что уже есть (фундамент)

- `server/api-clients.js`: таблица `app_api_clients` (ReplacingMergeTree), `createApiClient`
  (секрет показывается один раз), `listApiClients` (без хэшей), `deactivateApiClient`,
  `getActiveClientById`, `verifyApiClient`.
- `server/api-tokens.js`: SQLite-стор `api_tokens` (token, client_id, expires_at),
  `issue`/`verify`/`revoke`/`revokeByClientId`/`cleanupExpired`.
- Аудит-инфраструктура `server/audit-log.js`: авто-лог мутаций `/api` c выводом action из
  `resolveWriteAction` (механизм `user_create` и т.п.) + общий журнал аудита.
- Bearer-API `/api/v1` и события от него с актёром `api:<имя>` (см. ERP_USERS_API.md).

## 5. План реализации

### Шаг 1 — `server/api-clients.js`

- `recreateApiClient(clientId)`: новые client_id + секрет под тем же именем; старый
  client_id деактивируется, его токены отзываются; креды возвращаются один раз.
- `activateApiClient(clientId)`.
- `registerApiClient({ name, clientId, clientSecret })`: ручные креды. Валидация:
  имя непустое; client_id 12–64 символа, charset `[A-Za-z0-9._:-]`, уникальность
  (409 `client_id_taken`); секрет 12–512 символов.
- Тесты на новое.

### Шаг 2 — `server/api-tokens.js`

- `listActiveTokens()`: по клиентам `{ clientId, count, expiresSoonestAt }` — только
  живые токены, сами значения наружу не отдаём.
- Активность и статистика для «Монитора»: таблица `api_client_stats(client_id TEXT
  PRIMARY KEY, last_used_at INTEGER, stats_day TEXT, tokens_issued_today INTEGER,
  requests_today INTEGER)` в той же SQLite. Счётчики и метка копятся в памяти стора
  при `issue` (обмен токеном) и успешном `verify` (API-запрос) и сбрасываются в SQLite
  одним флешем не чаще раза в 60 сек на клиента — на запросе ERP записи нет; рестарт
  теряет не более минуты статистики. При смене дня счётчики обнуляются.
  Чтение: `getClientStats(clientIds)` → `{ lastUsedAt, tokensIssuedToday, requestsToday }`.
- Тесты на новое.

### Шаг 3 — `server/api-integration-routes.js` (новый) + монтаж

Роуты под префиксом `/api/admin/api-clients`:

| Метод и путь | Назначение |
| --- | --- |
| GET `/` | Список подключений: имя, client_id, статус, created/updated, токены `{count, expiresSoonestAt}`, lastUsedAt, ttlSec |
| POST `/` | Создать `{name}` → креды один раз (как CLI) |
| POST `/recreate` | `{clientId}` → новые client_id + секрет |
| POST `/manual` | `{name, clientId, clientSecret}` — свои креды |
| POST `/activate` | `{clientId}` |
| POST `/deactivate` | `{clientId}` + отзыв всех токенов |
| POST `/delete` | `{clientId}` — полное удаление строки (доработка после ревью) + отзыв токенов |
| POST `/revoke-tokens` | `{clientId}` — отозвать все токены |
| POST `/monitor` | `{clientId}` — панель «Монитор»: сторона NTA (активность, тестовый токен, TTL) + сторона ERP (счётчики за сутки, последний приход, последние операции из журнала) |
| POST `/verify-pair` | `{clientId, clientSecret}` — bcrypt-проверка пары |
| GET `/journal` | События из `audit_log` по нашим action'ам (без требования права `audit`). `?clientId=` — полный журнал одного подключения: админ-действия + операции Bearer-API (доработка после ревью) |

- `index.js`: монтаж после `requireSession` (рядом с `/api/rbac`).
- `rbac/api-map.js`: `/api/admin/api-clients` → `api-integration-erp`; `/monitor` и
  `/verify-pair` — в `READ_ONLY_POST_PATHS` (для них достаточно «Доступа», не спамят аудит).
- `audit-log.js`, `resolveWriteAction`: наши пути → action'ы `api_client_create`,
  `api_client_recreate`, `api_client_manual_register`, `api_client_activate`,
  `api_client_deactivate`, `api_client_tokens_revoke` + подписи
  `auditPage.action.*` в i18n ru/en.
- `listAuditEvents`: фильтр по списку action (для `/journal`) и по актёру `api:<имя>`
  (для блока «последние операции» в «Мониторе»).
- Тесты роутера/валидации.

## 6. Чек-лист ручной проверки

1. Пункт меню виден под Administrator; в «Роли» появился тумблер «API интеграция ERP»;
   у роли без доступа пункта нет, прямой URL и API дают 403.
2. Создать подключение: креды показаны один раз, копируются, строка появилась в таблице.
3. Свои креды: сохранить пару 12+ символов; коллизия client_id → 409; короткое → ошибка валидации.
4. Пересоздать: новые client_id + секрет; старая строка «отключена»; токен, полученный
   по старым кредам, умер (401).
5. Отключить: `/oauth/token` по этим кредам → 401 `invalid_client`. Включить — снова работает.
6. Отозвать токены: получить токен curl-ом → нажать → старый токен 401.
7. Монитор: обе стороны панели; после curl-обмена токеном счётчик «обменов токеном»
   вырос, «последний приход» обновился; до первого обмена — «никогда» и нули.
8. Проверить пару: верный секрет → «совпадает», неверный → «не совпадает».
9. Последняя активность: после curl-обмена токеном метка обновилась.
10. Журнал: события создан/пересоздан/отключён… с актёром-админом видны на странице и в
    общем журнале аудита.
11. CLI `api-client-create.js` по-прежнему работает поверх той же таблицы.

## 8. Доработки после ревью UI (2026-10-22)

Первая версия страницы проверена Владиславом; найдены баги и собраны правки по UX.

### Баги

1. **Цвет шрифта в инпутах нечитаем** — инпуты были «голые» (стиль вкладки диагностики).
   Фикс: все инпуты переведены на класс `input` + обёртки `field`, как на странице «Клиенты».
2. **«Piter-ix» выглядит как значение поля** — это был placeholder; кнопка «Создать» при
   этом заблокирована (поле пустое). Фикс: нейтральный placeholder, создание уезжает в модалку.
3. **Свои креды всегда падали с «clientSecret is not defined»** — ReferenceError: в запрос
   уходила несуществующая переменная вместо `manualSecret`. Фикс + клиентская валидация:
   кнопка активна только при заполненном названии, client_id ≥ 12, секрет ≥ 12; ошибки — в модалке.

### Редизайн по референсу «Клиенты»

- **Шапка** `page-head`: заголовок «API интеграция ERP», описание; справа «Обновить» (ghost)
  и «Создать» (primary, только при праве записи).
- **Таблица** — компонент `DataTable` (как у клиентов): инпут поиска, изменение ширины колонок,
  меню настройки видимости полей, пагинация (15/стр). Статус — `Badge` с точкой (как колонка
  состояния клиентов). Строка — `cursor: pointer`, клик открывает карточку.
- **Действия** — иконки с тултипами в конце строки: карточка, Пересоздать, Отозвать токены,
  Отключить/Включить (pause/play), Удалить (trash). Разрушительные — с подтверждением.
- **Модалка «Создать»**: переключатель «Сгенерировать автоматически» / «Указать свои» —
  при «своих» появляются три инпута (название, client_id, client_secret).
- **Модалка-карточка подключения** (клик по строке): дублирует все данные строки и все кнопки
  с функционалом; плюс блок «Монитора», **полный журнал подключения** (вместо «последних 5
  операций»), форма «Проверить пару» с подставленным client_id.
- **Модалка «Креды выпущены»** открывается сразу после создания/пересоздания (не нужно
  скроллить наверх): client_id, секрет (только для генерации), кнопка «Скопировать всё»
  одним нажатием, предупреждение «показывается один раз».
- С главной страницы убраны: блоки создания, «Проверить пару», панель «Монитора», блок
  выданных кредов. **Общий журнал под таблицей остаётся** (события всех подключений).
