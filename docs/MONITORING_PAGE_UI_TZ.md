# ТЗ: страница «Мониторинг»

Задача для UI-разработчика. Бэкенд уже отдаёт данные. Пункт меню «Мониторинг» уже есть
(первый в «Главном», `NAV` в `components/shell.jsx`) и открывает заглушку «Страница в
разработке» (`deploy/ui/app/public/pages/monitoring.jsx`, функция `PageMonitoring`). Её нужно
заменить этим экраном. Имя функции и запись в `public/data/page-chunks.manifest.js` не менять.

## 1. Зачем

Дежурный открывает страницу и сразу видит две вещи: идёт ли атака и жива ли сама система.
Сейчас для этого нужно пройти «Диагностику» по вкладкам и отдельно страницу коллекторов,
и всё это видит только администратор.

Пустой список атак не должен выглядеть как «всё хорошо», если детекция отстала или коллектор
не шлёт данные. Поэтому атаки и проблемы системы стоят на одном экране.

## 2. Доступ

- Страница `monitoring`, раздел «Главное», первый пункт меню. Адрес `#monitoring`.
- Права настраиваемые, строка уже есть в матрице «Пользователи и права». По умолчанию
  страница включена всем ролям, кроме клиентского кабинета. Новые права дописываются при
  старте UI, уже выданные роли не перетираются.
- Все данные брать только из `/api/monitoring/*`. Ответ всегда `{ "data": ... }`, ошибка —
  `{ "error": "текст" }`. `/api/detection/*` и `/api/diagnostics/*` не вызывать: они
  доступны только администратору.
- Ссылку у проблемы показывать, только если у пользователя есть доступ к целевой странице.
  У «Диагностики» доступ отдельный. Нет доступа — только текст, без стрелки.

## 3. Разметка

```text
┌──────────────────────────────────────────────────────────────────────┐
│ Мониторинг   ● 2 атаки   ● 1 критичная проблема   ● 3 предупреждения  │
│              данные детекции на 11:49 МСК · обновлено 10 с назад     │
├───────────────────────────────────────────────┬──────────────────────┤
│ АКТИВНЫЕ АТАКИ            [ ] Показать пики   │ ПРОБЛЕМЫ СИСТЕМЫ     │
│ ┌───────────────────────────────────────────┐ │ ● Коллекторы         │
│ │ ● идёт   ПИН · провайдер · амплификация   │ │   M9 не шлёт данные  │
│ │ 12,4 Гбит/с лишнего · ×3,1 к норме часа   │ │   с 11:41 (15 мин) → │
│ │ идёт 23 мин · пик 18 Гбит/с в 11:48       │ │ ▲ Worker             │
│ │ куда 188.143.x.x · вход sw-msk-1          │ │   traffic_1m отстаёт │
│ └───────────────────────────────────────────┘ │   на 12 мин        → │
│ ┌───────────────────────────────────────────┐ │                      │
│ │ ◐ затихает  91.x.x.0/24 · атака по сети   │ │ В порядке: ClickHouse│
│ │ было 2,1 Гбит/с лишнего · тихо 2 из 3 мин │ │ детекция, SNMP       │
│ └───────────────────────────────────────────┘ │                      │
└───────────────────────────────────────────────┴──────────────────────┘
```

Атаки занимают примерно две трети, проблемы — треть. Если окно уже 1100 px, проблемы
уходят под атаки, верхняя строка остаётся наверху.

### 3.1. Верхняя строка

| Элемент | Откуда | Цвет |
|---|---|---|
| «N атак» | `data.attacks`, без пиков | красный, если больше 0; серый «атак нет» |
| «N критичных» | проблемы `level = critical` | красный |
| «N предупреждений» | проблемы `level = warning` | жёлтый |
| «данные детекции на HH:MM МСК» | `meta.detectionMinute` | красный, если `meta.detectionStale` |
| «обновлено N с назад» | время последнего успешного ответа | серый; жёлтый, если запросы не проходят больше минуты |

`meta.detectionMinute` — это UTC-время минуты в виде `YYYY-MM-DD HH:MM:SS`, как в остальной
детекции. На экране показывать МСК. Свежесть решать по `meta.detectionStale`, не по часам
браузера. Рядом сервер отдаёт `detectionLagSec` и `detectionEmpty`.

Детекция всегда отстаёт: минута считается закрытой через 4 минуты и подписана своим началом.
На ШПД обычное отставание 6,5–7,2 минуты. Поэтому `detectionStale` включается только после
10 минут, а «данные на 11:49» в 11:56 — это норма, не ошибка.

Если проблем нет, вместо счётчиков проблем пишется зелёным «система в порядке».

## 4. Блок «Активные атаки»

`GET /api/monitoring/attacks` → `{ attacks, peaks, peaksError }`.

`attacks` — активные атаки, тот же объект, что на вкладке «Детекция → Активные».
`peaks` — обычные пики за последний час, по одному свежему на объект и сигнал. В счётчик
атак они не входят. `peaksError` — строка или `null`: если пики не прочитались, атаки всё
равно показать и под переключателем написать, что пики сейчас недоступны.

### 4.1. Карточка

| Что показать | Поле | Как |
|---|---|---|
| Состояние | `live.state` | `ongoing` → «идёт»; `fading` → «затихает»; нет `live` → «нет данных» |
| Объект | `name`, `scope` | «абонент» / «провайдер» / «сеть /24» для `client` / `provider` / `net` |
| Тип | `verdict.kind` | `volumetric` → «атака в сервер», `carpet` → «атака по сети», `syn_flood` → «SYN-флуд», `amplification` → «амплификация», `benign_peak` → «обычный пик» |
| Главный объём | `live.lastHotExcessBps` | «12,4 Гбит/с лишнего»; для `fading` — «было … лишнего» |
| От нормы | `verdict.hourRatio` | «×3,1 к норме часа» |
| Пик | `live.peakBps`, `live.peakMinute` | «пик 18 Гбит/с в 11:48» |
| Длительность | `startMinute` или `alertMinute` | «идёт 23 мин» |
| Затихание | `live.quietStreak`, `live.normalizeStreak` | только для `fading`: «тихо 2 из 3 мин» |
| Куда и вход | `investigate` | как колонки «Куда» и «Коммутатор вход» на вкладке «Активные» |

`live` есть только у `status = active`. Объём и пик — в бит/с с единицами, как `formatBps`
на странице детекции. Время — МСК, `HH:MM`.

Если `live.lastHotExcessBps` нет, главный объём брать из `alertByProto.all.bps` и подписать
«в момент срабатывания».

### 4.2. Порядок и пики

- Сначала «идёт», потом «затихает», внутри — по главному объёму, больше выше.
- «Показать пики» по умолчанию выключен. Состояние хранить в браузере под ключом
  `grapes-monitoring-show-peaks`.
- Когда включён, после атак показать `peaks`. Если в `attacks` всё же попал
  `verdict.kind = benign_peak`, его тоже считать пиком и не включать в счётчик.
- Карточка пика приглушена, без красной метки. Одинаковые `id` не дублировать.

### 4.3. Пустой список

- Атак нет и `meta.detectionStale = false`: «Атак нет», ниже серым «данные на HH:MM МСК».
- Атак нет и `meta.detectionStale = true` (отставание больше 10 минут): жёлтым «Атак не
  видно, но детекция отстала на N мин — список может быть неполным». N брать из
  `meta.detectionLagSec`. Если `meta.detectionEmpty`, вместо отставания написать «детекция
  за сутки не записала ни одной минуты». Если проверка детекции сама не ответила,
  `detectionLagSec` будет `null`: написать «свежесть детекции неизвестна».

Клик по карточке открывает экран атаки (раздел 6).

## 5. Проблемы системы

`GET /api/monitoring/problems`.

```json
{
  "data": {
    "meta": {
      "checkedAt": "2026-10-14T08:57:10.000Z",
      "detectionMinute": "2026-10-14 08:50:00",
      "detectionMinuteIso": "2026-10-14T08:50:00.000Z",
      "detectionLagSec": 430,
      "detectionStale": false,
      "detectionEmpty": false
    },
    "components": [
      { "id": "collectors", "title": "Коллекторы", "status": "critical" },
      { "id": "detection", "title": "Детекция", "status": "ok" },
      { "id": "worker", "title": "Worker", "status": "ok" },
      { "id": "clickhouse", "title": "ClickHouse", "status": "ok" },
      { "id": "enrichment", "title": "Обогащение", "status": "ok" },
      { "id": "snmp", "title": "SNMP", "status": "ok" }
    ],
    "problems": [
      {
        "id": "collectors:collector_offline:m9",
        "component": "collectors",
        "level": "critical",
        "title": "M9 не шлёт данные",
        "message": "Ни один источник коллектора не виден в окне живых потоков (5 минут).",
        "since": "2026-10-14T08:41:00.000Z",
        "link": "#collectors",
        "diagnosticsTab": null
      }
    ]
  }
}
```

`components` всегда шесть, в этом порядке. `status`: `critical`, если есть critical;
иначе `warning`; иначе `ok`.

Проблемы уже отсортированы: порядок компонентов, внутри сначала `critical`. `id` стабилен
между опросами.

Строка: значок уровня, `title`, `message`, «с HH:MM (N мин)» по `since`, стрелка.
Группу из четырёх и больше свернуть до двух строк и «ещё N». Внизу серым перечислить
компоненты со `status = ok`: «В порядке: ClickHouse, детекция, SNMP».

Куда ведёт стрелка:

| Компонент | `link` | `diagnosticsTab` |
|---|---|---|
| collectors | `#collectors` | `null` |
| detection | `#diagnostics` | `detection` |
| worker | `#diagnostics` | `worker` |
| enrichment | `#diagnostics` | `enrichment` |
| snmp | `#snmp` | `null` |
| clickhouse | `null` | `null` |

Вкладки диагностики в адресе не живут. Перед переходом на `#diagnostics` записать
`diagnosticsTab` в `sessionStorage` ключом `grapes-diagnostics-tab` — так страница
диагностики открывает нужную вкладку.

`since` — оценка, не отдельный журнал инцидентов:

- Коллектор и молчащий источник: последняя минута в `traffic_direction_1m` за сутки.
  Это не сырые потоки. Если сама сводка отстала, `since` покажет лаг сводки, и рядом
  будет проблема worker. Источника, которого в сводке не было, `since` нет. У DNS-источников
  (например `dns-netflow`) `since` всегда пустой: их данные идут в журнал DNS, а не в
  сводку потоков.
- Worker, обогащение, SNMP: из возраста текущей проверки или времени последнего прогона.
  Если возраст неизвестен, `since` равен `null`, длительность не показывать.
- Детекция: `since` — последняя записанная минута.

Коллектор без источников проблемой не считается. Коллектор `offline` — одна critical
на весь коллектор. У `online` каждый молчащий источник — отдельный warning.

Если не ответила одна проверка, остальные проблемы всё равно приходят, а у упавшей
появляется critical `check_failed` («Не удалось проверить …»). Если упал весь
`GET /problems`, красная плашка «Не удалось проверить систему», счётчики проблем — «?».

## 6. Экран атаки

Адрес `#monitoring?attack=<id>`, ссылку можно переслать. «← Мониторинг» возвращает на
`#monitoring`.

Путь через слеш (`#monitoring/attack/<id>`) не годится: приложение считает id страницы всё
до `?`, и такая ссылка откроет «Обзор». Параметры брать из `parseAppHash().params`, как на
страницах «Топ» и «Разбор трафика».

id события выглядит так: `provider|isp:verolayn|2026-10-12 10:47:00`,
`net|94.26.169.0/24|2026-10-13 18:01:00`. В нём есть `|`, `/`, пробел и двоеточие, поэтому
id всегда кодировать через `encodeURIComponent` — и в адресе страницы, и в пути запроса:
`/api/monitoring/attacks/${encodeURIComponent(id)}/history`.

`GET /api/monitoring/attacks/<id>` отдаёт событие и после закрытия: `status` бывает
`active`, `normalized`, `peak`. Нет события — `404` и `{ "error": "Атака не найдена" }`.

Сверху вниз:

1. Объект, тип объекта, тип атаки, состояние. «Началась HH:MM, сработала HH:MM».
   Если `status` не `active`, серая плашка «Атака завершена»: для `normalized` время из
   `normalizeMinute`, для `peak` — из `alertMinute`.
2. Плашка объёма: лишнее сейчас, пик, от нормы часа, норма часа
   (`verdict.hourCeiling` или `verdict.hourP95`). Образец — `AttackLoadBanner`.
3. График `GET /api/monitoring/attacks/<id>/history`. Окно начинается за 30 минут до
   `startMinute` (если его нет, до `alertMinute`). У активной атаки окно идёт до сейчас.
   У закрытой — до `normalizeMinute` плюс 30 минут, у пика — до `alertMinute` плюс
   30 минут, но не позже сейчас. Длиннее 16 суток сервер обрежет сам, фактические
   границы — `from` и `to` в ответе.
4. Куда, откуда, вход — из `investigate`.
5. Мусорный UDP — `GET /api/monitoring/attacks/<id>/asn`. Рисовать тем же `EventAsnTop`.
   Минута среза: `live.lastHotMinute`, иначе `focusMinute`, иначе `alertMinute`.
   Нет ни одной — `400` «Нет минуты среза», блок показать с этим текстом.
6. «Отчёт для фильтра» — `GET /api/monitoring/attacks/<id>/flowspec`, окно как
   `FlowspecReportModal`. Кнопку не показывать, если `ipMarkupEligible` ложно:
   провайдер и сеть — всегда, абонент — только когда `binding.bindMode !== 'ports'`.
   Нет минуты — `400` «Нет горячей минуты». Абонент на портах, если запрос всё же ушёл,
   отвечает «Отчёт только для сети, размеченной по IP».
7. Текст `alertText`, ниже `normalizeText`, если он есть.

Точки графика:

```json
{
  "eventId": "…",
  "scope": "provider",
  "scopeId": "isp:pin",
  "from": "2026-10-14 07:30:00",
  "to": "2026-10-14 09:00:00",
  "alertMinute": "2026-10-14 08:10:00",
  "points": [
    { "t": "2026-10-14 08:10:00", "bucketMs": 1728893400000, "bps": 300, "growthBps": 3, "baselineBps": 100 }
  ]
}
```

`bps` — трафик, `baselineBps` — норма. `growthBps` — во сколько раз трафик выше нормы;
норма уже посчитана как `bps / growthBps`. Нулевая или пустая точка нормы — линию нормы
в этой минуте не рисовать. Отметить на графике `alertMinute`. Провайдер на этом графике
есть: история детекции для `provider` отдаётся тем же запросом.

## 7. Запросы

| Метод | Назначение |
|---|---|
| `GET /api/monitoring/attacks` | активные атаки и пики за час |
| `GET /api/monitoring/attacks/:id` | одна атака, в том числе уже закрытая |
| `GET /api/monitoring/attacks/:id/history` | трафик и норма для графика |
| `GET /api/monitoring/attacks/:id/asn` | мусорный UDP на минуте среза |
| `GET /api/monitoring/attacks/:id/flowspec` | отчёт для фильтра |
| `GET /api/monitoring/problems` | проблемы системы |

Ресурс прав у всех этих путей — `monitoring`.

## 8. Обновление

- Список и экран атаки перезапрашивать раз в 30 секунд.
- Скрытая вкладка браузера запросы не шлёт. При возврате — один запрос сразу.
- Ошибка одного запроса не очищает экран: остаются последние данные, «обновлено N с
  назад» желтеет.

## 9. Приёмка

1. Пользователь без «Диагностики», но с «Мониторингом», видит атаки, проблемы и экран
   атаки. Стрелок в диагностику у него нет.
2. Во время атаки карточка показывает «идёт» и лишнее сверх нормы. Число совпадает с
   колонкой «Сейчас» на вкладке «Детекция → Активные».
3. «Показать пики» добавляет пики за последний час и не меняет счётчик атак. После
   перезагрузки положение переключателя сохраняется.
4. Ссылка `#monitoring?attack=<id>` в другом браузере открывает ту же атаку, в том числе
   уже закрытую. Проверить на атаке по сети: в её id есть `/`. У провайдера на экране
   есть график.
5. Остановленный grapes-worker появляется как critical. Коллектор, который перестал слать
   потоки, появляется через 5–6 минут, со временем последней минуты сводки.
6. При обычном отставании детекции в 7 минут проблем по детекции нет. Если она молчит
   больше 10 минут, строка «данные детекции…» красная, а пустой список атак получает
   предупреждение из п. 4.3.

## 10. Не входит в этот экран

- История закрытых атак и прошлых проблем: она остаётся на вкладке «Детекция → История».
- Подтверждение и «взять в работу».
- Звук и браузерные уведомления.
- Пороги детекции.
