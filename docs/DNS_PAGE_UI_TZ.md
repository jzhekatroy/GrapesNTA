# ТЗ: страница «DNS-запросы» — три топа и справочник резолверов

Задача для фронтенд/фулстек-разработчика NTAdmin. Схема ClickHouse со стороны
GrapesNTA уже готова, менять её не нужно.

## 1. Зачем

Страница есть, но ей не пользуются для того, ради чего её открывают. Разбор с
отделом ШПД дал две конкретные претензии.

Первая: в топе клиентов навсегда стоят собственные рекурсивные резолверы
оператора. Через них ходят все абоненты, миллионы запросов там — норма. Они
вытесняют то, ради чего в топ и смотрят: незнакомый адрес с аномальным
поведением оказывается на сороковой строке.

Вторая: не видно, куда идут запросы. Вопрос «на какие серверы он ломится»
сейчас можно закрыть только лентой последних событий, а она на периодах длиннее
шести часов схлопывается до 30 минут.

## 2. Механика целиком

Три симметричных топа за выбранный период: **клиенты**, **домены**,
**серверы**. Клик по строке любого топа становится фильтром — две другие
таблицы и лента пересчитываются под него. Выделение на графике сужает период.

Этого достаточно для рабочего сценария: выделили всплеск на графике, увидели в
топе клиентов незнакомый адрес, кликнули — в топе доменов его домены, в топе
серверов те, куда он обращается.

У адресов в топах появляется бейдж роли, если адрес есть в справочнике
резолверов. Над топом клиентов один переключатель «Скрыть резолверы»,
включённый по умолчанию.

Всё остальное на странице остаётся как есть.

## 3. Что делать

### 3.1. Топ DNS-серверов

Третья таблица рядом с существующими двумя. Колонки: IP сервера, бейдж роли,
запросы, ответы, NXDOMAIN, SERVFAIL, ошибки %. Сортировка по запросам.

Источник данных — по той же логике, что и остальные топы: на коротких периодах
(до 6 часов) сырой `default.dns_log`, на длинных — новый роллап
`default.dns_servers_1h`.

```sql
default.dns_servers_1h
  hour      DateTime('UTC')
  source_id LowCardinality(String)
  server_ip FixedString(16)
  queries   UInt64   -- запросы, отправленные на этот сервер
  responses UInt64   -- ответы, полученные от него
  nxdomain  UInt64
  servfail  UInt64
ENGINE = SummingMergeTree, ORDER BY (hour, source_id, server_ip), TTL 90 дней
```

`client_ip` и `server_ip` в `dns_log` — это роли, а не источник и получатель,
поэтому одна строка сервера покрывает обе стороны обмена. Формула ошибок та же,
что в остальных топах: `(nxdomain + servfail) / responses`.

Серверный модуль строится по образцу существующего `dnsTopClients` в
`server/dns-queries.js`: те же `buildRawDnsFilters` для сырого пути и
аналог `buildClients1hFilters` с `timeCol: 'hour'` для агрегата.

### 3.2. Фильтр по IP сервера

Клик по строке в топе серверов должен что-то делать, поэтому нужен фильтр
`server_ip` — сейчас его нет. Добавить в панель фильтров рядом с «Client IP» и
пробросить в API как `server_ip`, по образцу `client_ip` (см. `clientIpFilterSql`
в `server/dns-queries.js` — для сервера нужна такая же функция по колонке
`server_ip`).

### 3.3. Справочник резолверов

Новая страница в разделе справочников. Эталон для копирования архитектуры —
`server/l3-prefixes.js` + `public/pages/cidr.jsx`: `ReplacingMergeTree` плюс вью
`_enabled`, запись через INSERT новой версии строки, удаление через `DELETE FROM`,
переключатель `enabled` через INSERT с новым `updated_at`.

```sql
default.net_dns_resolvers
  resolver_id  String                 -- ПЕРВИЧНЫЙ КЛЮЧ (ORDER BY resolver_id)
  prefix       String                 -- IP или CIDR: '8.8.8.8/32', '91.196.252.0/24'
  family       UInt8   DEFAULT 0      -- 4 | 6, выводится из prefix
  role         LowCardinality(String) -- resolver | client | public
  display_name String  DEFAULT ''
  comment      String  DEFAULT ''
  enabled      UInt8
  source       LowCardinality(String) DEFAULT 'manual'  -- UI пишет 'webui'
  updated_at   DateTime DEFAULT now()
ENGINE = ReplacingMergeTree(updated_at) ORDER BY resolver_id
```

Читать всегда из вью `default.net_dns_resolvers_enabled` — она отдаёт только
включённые записи.

`resolver_id` генерирует UI (например `crypto.randomUUID()`), пользователю он не
показывается. В таблице выводится `display_name`.

Роли и их смысл:

| role | Значение | Где встречается |
|---|---|---|
| `resolver` | Собственный рекурсивный резолвер оператора | В топе клиентов |
| `client` | Резолвер абонента | В топе клиентов |
| `public` | Публичный резолвер | В топе серверов |

Публичные (`8.8.8.8`, `1.1.1.1`, `9.9.9.9`, `77.88.8.8` и прочие) уже засеяны
миграцией. Свои и клиентские оператор добавляет сам — из разговора это резолверы
ПИН и Орбитали.

### 3.4. Бейджи и переключатель

В топе клиентов и в топе серверов рядом с IP выводится бейдж, если адрес
попадает в один из включённых префиксов справочника. Текст бейджа — `display_name`
либо название роли, если имя пустое.

Над топом клиентов — переключатель **«Скрыть резолверы»**, включён по умолчанию.
Он убирает из таблицы строки с ролью `resolver` или `client`. Данные при этом не
меняются: это фильтр отображения, а не исключение трафика.

Отдельно и важно: это **не** `net_flow_exclusions`. Там правило физически
выбрасывает трафик, и его нет ни в `flows_raw`, ни в экспорте. Здесь всё
наоборот — запросы через резолвер нужны целиком, потому что именно внутри них
живут абоненты, к которым потом придётся спускаться. Прячется одна строка в
таблице, не более.

Сопоставление адреса с префиксом лучше делать на стороне ClickHouse через
`isIPAddressInRange`, чтобы не тащить справочник в браузер.

### 3.5. Бейдж «внешний»

Если адрес не попадает ни в один префикс из `default.net_l3_prefixes_enabled` —
рядом с ним выводится бейдж `внешний`. Это ответ на вопрос из разбора про адрес
`193.109.89.198`: первое, что нужно знать про незнакомый IP в топе, — наш он или
чужой.

Бейдж выводится в обоих топах адресов и в ленте событий. Фильтра по нему делать
не нужно.

## 4. Чего делать не нужно

- Детекторы аномалий, алерты, автоматическая подсветка подозрительного.
- Итоговые карточки над графиком, чипсы активных фильтров, переходы в раздел
  потоков.
- VLAN. В `dns_log` такого поля нет, это работа в коллекторе и отдельная задача.
- Любая фильтрация, которая удаляет данные. Справочник влияет только на показ.

## 5. Миграции на стороне сервера

Обе уже в репозитории GrapesNTA, применяются администратором:

```bash
clickhouse-client --multiquery < deploy/clickhouse/dns_servers_1h.sql
clickhouse-client --multiquery < deploy/clickhouse/net_dns_resolvers.sql
```

Первая создаёт роллап и заполняет его из `dns_log` за доступную глубину
(сырой лог живёт 30 дней, роллап — 90, поэтому более старые часы останутся
пустыми). Вторая создаёт справочник и засевает публичные резолверы.
