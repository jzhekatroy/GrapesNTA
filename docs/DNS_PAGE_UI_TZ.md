# ТЗ: разделить DNS-обзор и «Разбор DNS»

Задача для фронтенд/фулстек-разработчика NTAdmin. ТЗ составлено после проверки
актуального `main` NTAdmin на коммите `68c64e7`.

## 1. Задача

Текущая страница `#dns` одновременно пытается решать две разные задачи:

1. Оперативный обзор: есть ли DNS-трафик, отвечают ли серверы, кто создаёт
   основную нагрузку.
2. Исследование: найти запросы конкретного IP или домена, выбрать тип запроса и
   результат ответа, построить график по этим условиям.

Из-за смешения задач над обзорным графиком появилась строка фильтров. Она
выглядит как общий фильтр страницы, но на периодах больше шести часов разные
агрегаты поддерживают разные поля. Например, выбранный `QTYPE` меняет часть
таблиц, но не меняет график. Пользователь не получает ни результата, ни
сообщения, что условие проигнорировано.

Нужно разделить обзор и исследование на две соседние страницы, не смешивая
DNS-поля с конструктором flow-запросов:

```text
Обзор
└── DNS

Анализ трафика
├── Разбор трафика
└── Разбор DNS
```

«Разбор DNS» должен выглядеть и вести себя как «Разбор трафика», но работать со
своей моделью данных и DNS-терминами.

## 2. Навигация

- Существующий маршрут `#dns` сохранить и превратить в страницу
  **«Обзор → DNS»**, чтобы не ломать ссылки.
- Добавить маршрут `#dns-explorer` с названием **«Разбор DNS»** в секцию
  «Анализ трафика», сразу после «Разбор трафика».
- Добавить страницу в `app-pages.json`, маршрутизацию, RBAC API map и права по
  образцу `explorer`.
- Не добавлять переключатель «Flow / DNS» внутрь существующего Explorer.
  Источники, измерения и условия слишком разные; общий экран будет скрывать
  половину полей при каждом переключении режима.

## 3. «Обзор → DNS»

Это страница, которую открывают, чтобы сразу увидеть общую картину. На ней нет
конструктора поиска и нет полей `QTYPE`, `RCODE`, домен, Client IP, Server IP.

Глобальные элементы страницы:

- период;
- коллектор/источник;
- часовой пояс.

Они применяются ко всем обзорным блокам.

### 3.1. График DNS-активности

Оставить текущий график, но заменить технические подписи человеческими:

| Сейчас | Нужно |
|---|---|
| `Запросы` | `Запросы` |
| `Ответы` | `Все ответы` |
| `NXDOMAIN` | `Домен не найден` |
| `SERVFAIL` | `Ошибка DNS-сервера` |

В tooltip можно оставить технический код:

- `Домен не найден (NXDOMAIN)`;
- `Ошибка DNS-сервера (SERVFAIL)`.

Важно объяснить модель данных: «Все ответы» уже включают успешные ответы,
NXDOMAIN и SERVFAIL. Последние две линии — подмножества ответов, а не
дополнительный объём поверх зелёной линии.

Выделение диапазона на графике меняет глобальный период обзора, но не создаёт
скрытый поисковый фильтр.

### 3.2. Три топа под графиком

Оставить три топа, как на странице «Топ ASN»:

1. **Источники запросов**
2. **Домены**
3. **DNS-серверы**

Текущие названия заменить:

| Сейчас | Нужно |
|---|---|
| `Топ клиентов` | `Источники запросов` |
| `IP клиента` | `IP-адрес` |
| `Топ доменов` | `Домены` |
| `Топ серверов` | `DNS-серверы` |
| `IP сервера` | `IP-адрес` |

Причина: `client_ip` — DNS-роль, а не карточка абонента. За адресом может быть
абонент, NAT, сервер или резолвер оператора.

Колонки NXDOMAIN/SERVFAIL также перевести:

| Сейчас | Нужно |
|---|---|
| `NXDOMAIN` | `Не найдено` |
| `SERVFAIL` | `Сбои DNS` |
| `Ошибки, %` | `Сбои DNS, %` |

`Сбои DNS, %` считать только так:

```text
SERVFAIL / все ответы × 100
```

Не включать NXDOMAIN в процент сбоев и не красить строку как аварию только из-за
высокого NXDOMAIN. NXDOMAIN — корректный ответ «домен не существует»; он
интересен для анализа, но сам по себе не означает поломку DNS.

Клик по строке топа не фильтрует обзор. Он открывает `#dns-explorer` и
подставляет соответствующее условие:

- источник → `IP источника = ...`;
- домен → `Домен = ...`;
- DNS-сервер → `IP DNS-сервера = ...`.

Пользователь видит заполненный конструктор и сам нажимает «Построить».

### 3.3. Известные DNS-резолверы

Над топом «Источники запросов»:

```text
☑ Скрыть резолверы из списка        [Настроить список]
```

- переключатель включён по умолчанию;
- «Настроить список» ведёт на существующий маршрут `#dns-resolvers`;
- tooltip переключателя:
  «Резолверы обслуживают много пользователей и обычно занимают верхние строки.
  Список настраивается вручную».

Справочник уже реализован в «Модель сети → DNS-резолверы». Не создавать второй
справочник. Сопоставление с `net_dns_resolvers_enabled` и бейджи ролей оставить.

Скрытие резолверов — только отображение топа. Данные не удаляются и не
исключаются из ClickHouse.

### 3.4. Последние события

Под топами оставить таблицу **«Последние DNS-события»**, по аналогии с
последними flow:

- последние 50 строк для выбранного источника;
- сортировка от новых к старым;
- без поисковой строки;
- явно написать в подзаголовке «Последние 50 событий»;
- использовать человеческие названия результата ответа;
- технический RCODE можно оставить в tooltip/деталях.

Эта таблица — оперативная лента, а не результат поиска.

## 4. «Анализ трафика → Разбор DNS»

Это отдельная страница, визуально и механически повторяющая «Разбор трафика»:

1. период;
2. метрика;
3. группировка;
4. панель условий;
5. кнопка «Построить»;
6. график;
7. таблица результата.

Не копировать все flow-поля. Использовать общие UI-компоненты Explorer, но
отдельный каталог DNS-измерений и отдельные API/SQL.

### 4.1. Запуск запроса

- Изменение черновика условий не запускает API автоматически.
- Запрос выполняется только после нажатия **«Построить»**.
- На экране различаются «черновик» и «последний применённый запрос», как в
  Explorer.
- Все результаты — график и таблица — строятся по одному снимку применённых
  условий.
- Условие нельзя молча игнорировать. Если сервер не может выполнить точный
  запрос, API возвращает явную ошибку, а UI показывает её пользователю.

### 4.2. Метрики

Минимальный набор:

- Запросы/с
- Все ответы/с
- Домен не найден/с
- Ошибки DNS-сервера/с
- Всего запросов
- Всего ответов

Названия `NXDOMAIN` и `SERVFAIL` в основном UI не использовать.

### 4.3. Группировки

Минимальный набор:

- IP источника
- Домен
- IP DNS-сервера
- Тип запроса
- Результат ответа

Как в Explorer, без группировки график показывает одну суммарную линию. При
выбранной группировке — top-N серий и таблицу всех возвращённых групп в пределах
серверного лимита.

### 4.4. Условия

Минимальный каталог:

| Поле | Операторы |
|---|---|
| IP источника | равно, не равно, входит в CIDR |
| Домен | равно, содержит, не содержит |
| IP DNS-сервера | равно, не равно, входит в CIDR |
| Тип запроса | равно, не равно, один из |
| Результат ответа | равно, не равно, один из |
| Источник/коллектор | один из |

Человеческие названия:

| Техническое поле | UI |
|---|---|
| `client_ip` | `IP источника` |
| `server_ip` | `IP DNS-сервера` |
| `query_name` | `Домен` |
| `qtype` | `Тип запроса` |
| `rcode` | `Результат ответа` |

Значения результата:

- Успешно (`NOERROR`, код 0)
- Ошибка DNS-сервера (`SERVFAIL`, код 2)
- Домен не найден (`NXDOMAIN`, код 3)
- Другой код

### 4.5. Предлагаемые значения

Поля не должны быть только пустыми текстовыми input. По образцу Explorer
показывать реальные/известные варианты:

- **Тип запроса:** A, AAAA, PTR, MX, TXT, NS, CNAME, SRV и другие наблюдаемые
  значения; рядом можно показывать количество за выбранный период.
- **Результат ответа:** фиксированный список с человеческими названиями.
- **Домен:** поиск по наблюдаемым доменам с debounce; не загружать весь словарь
  в браузер.
- **IP источника:** подсказки из наблюдаемых top IP; показывать бейдж
  резолвера/внешнего адреса.
- **IP DNS-сервера:** подсказки из наблюдаемых серверов и
  `net_dns_resolvers_enabled`, с `display_name`.
- **Источник/коллектор:** существующий каталог DNS-источников.

Выбор подсказки добавляет условие, а не запускает запрос.

### 4.6. Период и точность

Не вводить отдельный лимит периода для «Разбора DNS». Использовать общий выбор
периода, как в «Разборе трафика». Фактическая глубина определяется retention
данных (`dns_log` сейчас хранится 7 дней).

Сервер может выбрать raw или агрегат только при условии, что результат
семантически одинаков:

- агрегат содержит все выбранные условия и группировки;
- ни одно условие не теряется;
- метрика считается по той же формуле.

Если подходящего агрегата нет — выполнять точный запрос к raw. Не повторять
текущую ситуацию, когда на периоде больше шести часов `dns_activity_5m` молча
игнорирует QTYPE/RCODE/IP/домен.

Таймаут или превышение ресурса показывать как ошибку запроса с предложением
сузить период/условия. Не подменять результат данными за последние 30 минут без
явного согласия пользователя.

### 4.7. URL и переходы

- Применённый запрос сериализуется в hash/query params по образцу Explorer.
- Ссылку можно скопировать и открыть с теми же условиями.
- Переход из топа обзора открывает заполненный черновик; запрос автоматически
  не запускается.
- Кнопка «Вернуться в обзор DNS» ведёт на `#dns`.

## 5. Что удалить из текущей страницы

Из `PageDnsQueries` удалить обзорную строку:

- QTYPE
- RCODE
- Поиск домена
- Client IP
- Server IP
- «Сбросить фильтры»

Не переносить этот JSX целиком. Условия должны стать нормальным конструктором в
`PageDnsExplorer`.

Также удалить автоматические API-запросы после каждого изменения input. В
обзоре поисковых input больше нет, а в разборе используется кнопка «Построить».

## 6. Backend/API

Рекомендуемое разделение:

- текущие обзорные endpoints оставить для `#dns`, но убрать из них поисковые
  параметры;
- добавить отдельный endpoint выполнения DNS-разбора;
- добавить endpoints подсказок для домена, IP источника и IP DNS-сервера;
- добавить строгую серверную валидацию каталога полей, операторов, метрик и
  группировок — не принимать произвольные SQL-выражения с клиента.

Клиент отправляет структурированный запрос по образцу Explorer:

```json
{
  "range": "24h",
  "metric": "queries_per_sec",
  "groupBy": ["query_name"],
  "filters": [
    { "field": "client_ip", "op": "eq", "value": "188.143.128.3" },
    { "field": "rcode", "op": "eq", "value": 3 }
  ]
}
```

API возвращает:

- точки графика;
- серии/легенду;
- строки таблицы;
- фактический период;
- источник данных (`raw`/конкретный aggregate);
- время выполнения;
- признак усечения top-N.

## 7. Приёмка

1. В меню есть «Обзор → DNS» и «Анализ трафика → Разбор DNS».
2. На DNS-обзоре нет QTYPE/RCODE/IP/domain input.
3. График использует человеческие названия, технические коды доступны в
   подсказке.
4. Под графиком показаны три топа: источники запросов, домены, DNS-серверы.
5. В топах NXDOMAIN не включается в «Сбои DNS, %».
6. Рядом со скрытием резолверов есть рабочая ссылка «Настроить список».
7. В обзоре показаны последние 50 DNS-событий.
8. Клик по строке топа открывает «Разбор DNS» с заполненным условием.
9. Изменение условия в «Разборе DNS» не выполняет запрос до нажатия
   «Построить».
10. График и таблица используют одинаковый набор применённых условий.
11. QTYPE меняет график и на периоде больше шести часов либо запрос завершается
    явной ошибкой; молчаливого игнорирования нет.
12. Значения полей предлагаются из реальных данных/справочников.
13. Применённый запрос можно открыть по ссылке.

## 8. Не делать в этой задаче

- Не объединять flow и DNS в одном конструкторе.
- Не добавлять детекторы аномалий и автоматические алерты.
- Не удалять DNS-данные при скрытии резолверов.
- Не добавлять VLAN: поля нет в `dns_log`.
- Не создавать второй справочник резолверов.
